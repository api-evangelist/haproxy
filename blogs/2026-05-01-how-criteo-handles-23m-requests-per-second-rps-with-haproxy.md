                <p>Criteo handles 23 million requests per second (RPS) while maintaining peak performance and minimizing downtime. For most organizations, handling that level of traffic is just a theoretical stress test — a <em>what-if</em> scenario should their infrastructure ever be overwhelmed by an unexpected wave of requests. But for Criteo, 23 million RPS is just another Tuesday.</p><p>As the largest independent AdTech company, Criteo processes 9 billion bid requests every day across three continents and six data centers. Their infrastructure is built on bare-metal hardware, with over 30,000 servers. This scale requires an infrastructure that moves beyond manual configuration. To manage the massive flow of traffic, Criteo transitioned from vendor-locked hardware appliances to a fully <strong>automated <a href="http://production.int.haproxy.com/glossary/what-is-load-balancing-as-a-service-lbaas">Load Balancing as a Service (LBaaS)</a> platform built on HAProxy</strong>.</p>
                
            
                <img alt="" height="1016" src="https://cdn.haproxy.com/img/containers/posts/day1-criteo-5.png/c422e0478ef177262975c31076229185/day1-criteo-5.png" width="1800" />
                
            
                <p>SRE Basha Mougamadou explained at HAProxyConf how Criteo automates its load balancing stack to improve certificate management, backend scaling, and CPU efficiency.</p>
                
            
                
            
                <h2 id="moving-to-a-runtime-first-philosophy">Moving to a runtime-first philosophy</h2><p>Handling 1 terabit per second across six data centers means any change to the system must be efficient. Criteo moved away from traditional configuration management and made the <strong>HAProxy</strong> <strong>Runtime API the primary interface for all operational changes</strong>. This allows the infrastructure to scale and update without manual intervention.</p><p>The scale of the operation makes this approach necessary. Because certificates and backends must be continuously updated and scaled, the system requires a high level of automation. If these events required manual work or process restarts, the overhead would quickly add up.</p><p>To avoid this, Criteo designed a system where the configuration remains static while the internal state of the load balancer changes dynamically. This shift removes the operational cost associated with high-frequency updates.</p><h2 id="automating-tls-certificate-management">Automating TLS certificate management</h2>
                
            
                <img alt="" height="900" src="https://cdn.haproxy.com/img/containers/posts/security-lock-on-a-network-grid.jpg/fca5b7503722f7f4f2d039fc7b635dea/security-lock-on-a-network-grid.jpg" width="1800" />
                
            
                <p>Criteo maintains more than 5,000 TLS certificates with a 3-month validity period. These certificates require frequent rotation to maintain high security standards. Traditionally, updating a certificate required a manual configuration change. At Criteo&#039;s scale, the goal was to update security credentials automatically and in real time.</p><p>The team uses a three-part system to handle these updates. </p><ol start="1"><li><p>The certificate provider microservice manages the lifecycle and communicates with external authorities.</p></li><li><p>A control plane pulls renewed <a href="http://production.int.haproxy.com/glossary/what-is-transport-layer-security-tls">TLS</a> certificates and sends updates to provisioners.</p></li><li><p>These provisioners run locally on the load balancer nodes to update HAProxy.</p></li></ol><p>The provisioners<strong> use the HAProxy Runtime API to modify TLS certificates</strong> in memory. This process involves a four-step transaction. The system allocates a new certificate, sets its contents, commits the transaction, and adds it to the list. This method allows Criteo to renew roughly 100 certificates daily without manual config updates.</p><p>This architecture ensures that the file system and the running process stay synchronized. If a node restarts, it loads the latest certificates from disk. This automation helps address the industry trend toward shorter certificate lifespans, with proposals to reduce validity to as little as 47 days.</p><h2 id="dynamic-server-provisioning-for-rapid-autoscaling">Dynamic server provisioning for rapid autoscaling</h2><p>Criteo operates over 100,000 containers across Kubernetes and Apache Mesos clusters. Application instance counts fluctuate significantly throughout the day. One application may grow from 115 instances to 600 in a few hours.</p><p>Modern infrastructure requires a way to add and remove these backends instantly. Criteo uses <strong>dynamic servers</strong> introduced with full support in HAProxy 2.5 to manage these changes. Dynamic servers <strong>allows the team to provision and delete servers on the fly</strong>.</p><p>Named servers are a practical benefit of this approach. Where older server templates used generic indexes like <code>srv1</code> and <code>srv2</code>, dynamic provisioning gives each server a unique, descriptive name in the logs, making it significantly easier to trace errors to a specific container during an incident.</p><p>Removal follows a deliberate sequence: disable the server, drain active sessions, wait for the short &quot;removable state&quot; window, then delete. This prevents dropped requests during autoscaling and preserves consistent hashing for Criteo&#039;s Varnish cache layer, ensuring requests for a given path always reach the same cache node.</p><h2 id="aligning-software-threads-with-cpu-hardware">Aligning software threads with CPU hardware</h2>
                
            
                <img alt="" height="900" src="https://cdn.haproxy.com/img/containers/posts/automatic-cpu-binding-1748435967.jpg/1f37259564bec5862069d4c446369ef3/automatic-cpu-binding-1748435967.jpg" width="1800" />
                
            
                <p>At 23 million requests per second, small gains in CPU efficiency have a large impact on total capacity. Criteo uses AMD EPYC 7502P processors. These chips use a chiplet architecture where <a href="http://production.int.haproxy.com/glossary/what-is-a-cpu-core">CPU cores</a> are organized into Core Complex Dies.</p><p>Data travels much faster between cores on the same chiplet than it does across the I/O die. The latency for data sharing increases significantly when a <a href="http://production.int.haproxy.com/glossary/what-is-a-cpu-thread">thread</a> moves from one die to another. To solve this, Criteo uses new CPU policy features to group threads logically.</p><p>The team uses the <code>group-by-2-clusters</code> policy to bind HAProxy threads to the physical layout of the AMD chip. This keeps related threads on the same core complex, which helps the CPU share data more efficiently and reduces the need for the processor to move information across the entire chip.</p><p>Criteo’s tests showed that this configuration reduced context switching by 20%. This change frees up CPU cycles to handle actual request traffic.
